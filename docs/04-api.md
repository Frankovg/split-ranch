# 04 — REST API

Base URL `https://api.<domain>/v1`. JSON, UTF-8, `snake_case`. OpenAPI 3.1 generated by FastAPI is the contract; the mobile client types are hand-written mirrors today (`apps/mobile/src/features/groups/types.ts`), to be generated from OpenAPI later.

Groups replaced households and periods in migration 0006 (design: [egm/design_draft.md](egm/design_draft.md)). The routes (`/households/...`, `/periods/...`, `/transfers/...`) were renamed inside `/v1` because the mobile app is the only client and both phones are updated by hand.

## Conventions

| Topic | Rule |
|---|---|
| Auth | `Authorization: Bearer <Supabase access token>` on everything except `/healthz`, `/readyz`, `/config`. Sign-in, refresh and sign-out happen between the app and Supabase Auth; the API has no `/auth/*` routes |
| Tenancy | Group-scoped routes live under `/groups/{group_id}/…`. The server loads the caller's membership from the DB; non-members **and members who left** get **404** (not 403) to avoid leaking existence |
| Identity | `user_id`, `created_by`, `actor` never accepted in bodies; derived from the JWT |
| IDs | UUIDv7. Clients send `id` when creating expenses (optional) and payments (required) |
| Money | `{"amount_cents": 1250}` — integer euro cents (EUR only, no currency field) |
| Dates | `expense_date: "2026-03-14"` (calendar day in the group time zone); timestamps ISO-8601 UTC |
| Pagination | Keyset/cursor: `?limit=50&cursor=<opaque>` → `{"items": [...], "next_cursor": "..." | null}`. Default 50, max 200 |
| Filtering | Expenses and summary: `?from=2026-03-01&to=2026-03-31&category_id=…&payer_member_id=…&created_by_user_id=…&q=text` (dates inclusive) |
| Optimistic locking | Expense and payment responses carry `ETag: "<version>"`; expense `PATCH`/`DELETE` and payment transitions require `If-Match: "<version>"` → `412` if stale (body includes the current resource), `428` if missing |
| Idempotency | Creating an expense or payment is idempotent through its client-generated `id`: the same id and payload again returns the stored row (`200`); a different payload, or an id used in another group, is `409 id_conflict` |
| Errors | RFC 9457 `application/problem+json`: `{type, title, status, detail, code, errors?: [{loc, msg, type}]}` |
| Versioning | URL major version (`/v1`). Min supported app version returned in `X-Min-App-Version` (the app does not enforce it yet) |
| Rate limits | Planned: per user (e.g. 120 req/min) and per IP on public endpoints; `429` + `Retry-After`. Not built |

### Error codes (`code`)
`unauthenticated`, `token_expired`, `forbidden_role` (403), `not_found`, `validation_error`, `split_mismatch`, `invalid_split`, `invalid_ratios`, `invalid_payer`, `invalid_category`, `invalid_source`, `invalid_payment`, `version_conflict` (412), `precondition_required` (428), `id_conflict` (409), `invitation_expired` (410), `already_member` (409), `category_exists` (409), `category_archived` (409), `member_has_open_balance` (409), `group_has_open_balances` (409), `member_left` (409), `cannot_remove_self` (409), `confirm_name` (422), `payment_state_changed` (409), `rate_limited`.

Removed with periods: `period_locked`, `reason_required`, `period_state_changed`, `no_open_period`, `period_open`, `period_not_latest`, `last_admin`.

## Auth and current user

Token verification (FastAPI dependency `get_actor`):
1. Read the bearer token; decode the header, pick the key by `kid` from the project **JWKS** (`https://<project>.supabase.co/auth/v1/.well-known/jwks.json`, cached ~10 min, refetched on unknown `kid`). Library: `PyJWT` with `PyJWKClient`.
2. Verify signature with the asymmetric algorithm the project uses (ES256 by default; reject `HS256` and `none`), `iss = https://<project>.supabase.co/auth/v1`, `aud = authenticated`, `exp` (30 s leeway).
3. `role` claim must be `authenticated` (reject `anon` and `service_role` tokens).
4. `user_id = sub`. Call `ensure_user` (cheap upsert, cached per process for a few minutes).

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/me` | — | user + active memberships `[ {group_id, group_name, member_id, role, status} ]`; creates `app.users` on first call |
| PATCH | `/me` | `{display_name?, locale?}` | user |
| DELETE | `/me` | `{confirm: "DELETE"}` | *Not built yet.* Anonymise memberships (with admin hand-over), delete own data, then delete the Supabase auth user |

No group in the token (a user has several groups; membership is checked per request). We do not add custom claims to Supabase tokens.

## Groups and members

Every active member has the same rights; the admin (the creator, or whoever the role passed to) is the only one who removes members and deletes the group.

| Method | Path | Who | Notes |
|---|---|---|---|
| POST | `/groups` | any user | `{name, timezone?}` → creator becomes admin; default categories copied, default rule = equal |
| GET | `/groups` | any user | my groups (active memberships), oldest first |
| GET | `/groups/{gid}` | member | settings, members (`joined_at`, `left_at`, role, status), `my_member_id`, `my_role` |
| PATCH | `/groups/{gid}` | member | `{name?, timezone?}` |
| DELETE | `/groups/{gid}` | admin | `{confirm_name}` (must equal the name); soft delete; `409 group_has_open_balances` unless every net is 0 and no payment is waiting |
| POST | `/groups/{gid}/invitations` | member | → `{code, expires_at}`: the group's single join code, reused while valid (7 days), a new one otherwise |
| DELETE | `/groups/{gid}/invitations` | member | revoke the current code |
| GET | `/invitations/{code}` | authenticated | preview `{group_name, member_count, expires_at}`; `410 invitation_expired` |
| POST | `/invitations/{code}/accept` | authenticated | join (or rejoin); `409 already_member` |
| POST | `/groups/{gid}/members/me/leave` | member | `204`; `409 member_has_open_balance` unless my net is 0 and no payment of mine is `sent`/`disputed`. The admin role passes to the next active member; the last member leaving deletes the group |
| DELETE | `/groups/{gid}/members/{mid}` | admin | same rule as leave, for someone else; `409 cannot_remove_self` |

## Categories and rules

| Method | Path | Who |
|---|---|---|
| GET/POST | `/groups/{gid}/categories` | member |
| PATCH/DELETE | `/groups/{gid}/categories/{cid}` | member (DELETE = archive) |
| GET | `/groups/{gid}/split-rules` | member |
| PUT | `/groups/{gid}/split-rules/default` | member |
| PUT/DELETE | `/groups/{gid}/categories/{cid}/split-rule` | member |

Split rule payload (shared by rules, expense overrides and AI tools):

```json
{
  "split_type": "percentages",
  "shares": [
    {"member_id": "…juli", "basis_points": 6000},
    {"member_id": "…franco", "basis_points": 4000}
  ]
}
```

Pydantic models use a **discriminated union on `split_type`** (`EqualSplit`, `WeightsSplit`, `PercentagesSplit`, `ExactSplit`, `SingleSplit`, `PersonalSplit`) with `model_config = ConfigDict(extra="forbid", strict=True)`. The same JSON is what the database stores ([02](02-data-model.md#split-rules-as-json)). A rule change applies only to expenses created or explicitly re-split afterwards.

## Expenses and summary

| Method | Path | Notes |
|---|---|---|
| GET | `/groups/{gid}/expenses` | filters + cursor; newest `expense_date` first (the app groups by day) |
| GET | `/groups/{gid}/summary` | same filters → `{count, total_cents, by_category: [{category_id, total_cents}], by_payer: [{member_id, total_cents}]}` over live, non-personal expenses; `mine=true` sums only the caller's shares instead (their personal expenses included) |
| POST | `/groups/{gid}/expenses` | create; idempotent by `id`; payer must be an active member |
| GET | `/groups/{gid}/expenses/{eid}` | includes shares, `split_origin`, `rule_fallback`, `created_by_user_id`, `updated_by_user_id`, `can_edit` |
| PATCH | `/groups/{gid}/expenses/{eid}` | any member; `If-Match`; only `split`/`participants` re-split, an amount change re-allocates over the stored participants ([03 §4](03-business-rules.md#4-editing-expenses)); `409 member_left` if a former member is involved |
| DELETE | `/groups/{gid}/expenses/{eid}` | any member; `If-Match`; soft delete; optional `{reason}` |
| GET | `/groups/{gid}/expenses/{eid}/revisions` | history (the expense's rows in `history`) |
| POST | `/groups/{gid}/expenses/preview` | resolves shares without saving |

Create payload:

```json
{
  "id": "0193a7c2-…",
  "amount_cents": 10000,
  "description": "Supermercado",
  "category_id": "…",
  "payer_member_id": "…",
  "expense_date": "2026-03-14",
  "split": null,
  "participants": null,
  "source": "manual",
  "notes": null
}
```

`split = null` → resolved by precedence; `participants` = optional subset (makes it an override). `source` values other than `manual` are only accepted from server-side callers; a public client sending `ai_*` gets `422`.

## Balance and payments

| Method | Path | Who | Notes |
|---|---|---|---|
| GET | `/groups/{gid}/balance` | member | `{balances: [{member_id, paid_cents, owed_cents, net_cents, pending_out_cents, pending_in_cents}], suggestions: [{from_member_id, to_member_id, amount_cents}]}`. `net_cents` counts confirmed payments only; suggestions also count `sent` ones |
| GET | `/groups/{gid}/payments` | member | newest first, cursor; `?status=sent&status=disputed` |
| POST | `/groups/{gid}/payments` | the payer or the receiver | `{id, from_member_id, to_member_id, amount_cents, method, note?}` (`method`: required, one of `bizum`, `bank_transfer`, `cash`, `other`) → `201`; the payer creates it `sent`, the receiver `confirmed` (cash). Another member → `403` |
| GET | `/groups/{gid}/payments/{pid}` | member | with `ETag` |
| POST | `/groups/{gid}/payments/{pid}/confirm` | receiver | `{note?}`; `sent`/`disputed` → `confirmed` |
| POST | `/groups/{gid}/payments/{pid}/dispute` | receiver | `{note}` required; `sent` → `disputed` |
| POST | `/groups/{gid}/payments/{pid}/cancel` | payer | `{note?}`; `sent`/`disputed` → `cancelled` |

Transitions need `If-Match`; one not allowed from the current status is `409 payment_state_changed` with the current payment.
